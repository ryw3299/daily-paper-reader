## 摘要
大型语言模型（LLM）的最新进展为自动驾驶系统（ADS）创建自然语言接口提供了新机遇，使其不再局限于僵化的输入方式。本文旨在解决将人类语言的复杂性映射到模块化ADS软件结构化动作空间的挑战。我们提出了一个将基于LLM的交互层与广泛使用的开源软件Autoware相集成的框架。该系统使乘客能够发出高层指令，从查询状态信息到修改驾驶行为。我们的方法基于三个关键组成部分：交互类别的分类体系、用于命令翻译的以应用为中心的领域特定语言（DSL），以及一个保持安全性的验证层。两阶段LLM架构通过基于确定性执行状态提供反馈来确保高透明度。评估证实了系统的时序效率和翻译鲁棒性。仿真成功验证了所有五类交互类别下的命令执行。这项工作为模块化且注重安全的自主性技术栈中可扩展的、DSL辅助的交互奠定了基础。

## Abstract
Recent advancements in Large Language Models (LLMs) offer new opportunities to create natural language interfaces for Autonomous Driving Systems (ADSs), moving beyond rigid inputs. This paper addresses the challenge of mapping the complexity of human language to the structured action space of modular ADS software. We propose a framework that integrates an LLM-based interaction layer with Autoware, a widely used open-source software. This system enables passengers to issue high-level commands, from querying status information to modifying driving behavior. Our methodology is grounded in three key components: a taxonomization of interaction categories, an application-centric Domain Specific Language (DSL) for command translation, and a safety-preserving validation layer. A two-stage LLM architecture ensures high transparency by providing feedback based on the definitive execution status. Evaluation confirms the system's timing efficiency and translation robustness. Simulation successfully validated command execution across all five interaction categories. This work provides a foundation for extensible, DSL-assisted interaction in modular and safety-conscious autonomy stacks.

## 1. 核心问题与整体含义

- **研究动机**：模块化自动驾驶系统（如 Autoware）具备成熟的感知、规划与控制能力，但其交互接口通常是环境反应式或硬编码输入，乘客难以用自然语言表达高层意图。
- **核心问题**：如何将无限、连续的人类语言空间（指令 \(I\)）安全、可靠地映射到模块化 ADS 有限、结构化的动作空间（策略 \(P=\{A,C\}\)，含离散动作与连续参数）。
- **整体含义**：论文提出一个 LLM 驱动的"副驾驶"交互层，让乘客通过语音查询状态、设定目的地、调整驾驶偏好、请求局部机动或纠正系统误判，同时**不修改安全相关的驾驶功能**，语言解释与安全关键执行环路解耦。
- **定位差异**：区别于端到端 LLM 控制架构（如 DriveGPT4、LMDrive），本文聚焦高层交互而非底层控制信号生成。

## 2. 方法论

### 核心思想
- 以 LLM 作为语言到结构化命令的翻译骨干，输出符合自定义 DSL 的命令，再由独立的 ROS2 验证与接口节点校验并触发 Autoware 执行。

### 关键技术细节

- **交互分类体系（Taxonomy）**：将乘客交互划分为五类——
  - *Information*：查询车速、限速、到达时间等状态数据；
  - *Mission Control*：设定目的地、启动/停止自动驾驶；
  - *Configuration*：长期行为参数调整（速度/加速度上限、跟车距离）；
  - *Cooperation*：请求局部机动（变道、超车、转向），最终执行仍受系统安全检查约束；
  - *Intervention*：覆盖系统内部状态（如纠正误检红灯、幽灵障碍物、紧急停车）。
- **应用中心 DSL**：命令包含 `command_type`（类别）、`action`（动作）、`parameters`（名值对，如 `max_vel: 90.0`）。与 AutoIR 等模块中心 DSL 不同，该 DSL 按应用语义而非软件模块结构组织，因而对内部架构变化更鲁棒，且可迁移至其他模块化栈。
- **验证与接口层（安全机制）**：DSL 动作到 Autoware 具体执行（ROS2 topic/service/参数调整）的映射**必须手工显式构建**，仅允许白名单动作与经校验的参数边界，用以防御 LLM 幻觉、误解析或恶意指令。
- **两阶段 LLM 架构（透明反馈）**：
  1. 第一阶段：语音指令 + AV 状态信息 + 知识库（角色定义、DSL 规范、ICL 示例）→ 生成 DSL 命令；
  2. 命令经接口节点验证执行后，将**确定性成功/失败状态**连同原始意图回灌 LLM 进行第二次 API 调用，生成准确的乘客反馈，再经 TTS 转为语音播放。
- **模型与部署**：使用云端 Gemini 2.5 Flash-Lite，直接处理音频以绕过独立 STT 步骤，规避车载 GPU 限制。

## 3. 实验设计

- **数据集**：自建 \(N=200\) 条人工指令- DSL 命令配对数据集，五类交互大致均衡，另含一类"超出系统范围"的请求；指令在语气与直接程度上有所变化，部分 DSL 命令重复。指令经 TTS 合成为音频输入。
- **翻译评测（消融）**：Baseline（AV 状态 + 知识库 + ICL 示例）对比三种消融——No AV Status、Zero-Shot（去 ICL）、KB-Only（去两者），指标为翻译准确率与响应时间 \(t_r\)。
- **对比基准**：与 Song et al.（Autoware.Flex）比较准确率与延迟；因原始数值不可得，其箱线图数据由数字图像提取工具从已发表图中获取（非完全同构实验：不同数据集、不同 LLM、不同 DSL）。
- **仿真验证**：基于真实街道拓扑的自定义矢量地图，设计含六个时间点（\(t_0\)–\(t_5\)）的单一场景，覆盖全部五类交互（启动/停止、红灯干预、状态查询、路口改道直行、限速调整），重复 \(N=30\) 次，统计任务成功率（TSR）与组件延迟。
- **测试平台**：Intel Core i5-14500 桌面机运行 Autoware planning simulation；另在真实研究车辆上确认了基础命令执行（未做定量评估）。

## 4. 资源与算力

- 论文**未报告任何 GPU 型号、数量或训练时长**。
- 系统不涉及模型训练或微调，LLM 通过云端 API（Gemini 2.5 Flash-Lite）调用；本地仅运行 Autoware 规划仿真于桌面 CPU 上。

## 5. 实验数量与充分性

- **实验组数**：约 4 组翻译消融（每组 \(N=200\)）+ 1 组端到端仿真可靠性实验（\(N=30\)）+ 1 次真车基础功能确认，规模较小。
- **充分性评价**：
  - 消融设计清晰，能有效定位 ICL 示例的关键作用，具有一定说服力；
  - 但翻译数据集为作者自建、规模有限，且指令与 DSL 配对由人工构造，可能存在分布偏置；
  - 端到端验证仅覆盖**单一场景**，30 次重复主要反映 API 稳定性而非场景多样性；
  - 与 Song et al. 的对比因数据集、模型、DSL 均不同，且对方数据经图像数字化提取，**公平性有限**，作者亦承认"非完全相同的实验设置"。
- **总体**：实验客观性尚可（有消融、有重复运行、报告失败原因），但覆盖面偏窄，外部效度不足。

## 6. 主要结论与发现

- Baseline 翻译准确率达 **97.0%**，平均翻译时间 \(t_r=1.723\) s（中位数 1.669 s）。
- 移除 AV 状态信息影响可忽略（96.0%），说明多数测试指令不依赖上下文；移除 ICL 示例导致性能骤降（Zero-Shot 73.0%，KB-Only 66.3%），**ICL 示例是鲁棒翻译的关键**。
- 延迟不受消融配置显著影响，推理时间由核心生成任务主导。
- 相比 Song et al.（87.0% 准确率），本文准确率更高、延迟更低且抖动更小，作者归因于应用中心 DSL 简化了翻译任务。
- 仿真中 30 次运行 TSR 达 **96.7%**（29/30），唯一失败源于 LLM 反馈生成时的 API 服务器错误。
- 命令执行延迟均值 5.737 ms（中位数 0.461 ms，标准差 8.491 ms，分布右偏，源于 topic 发布与服务调用的混合），相对 LLM 推理可忽略；反馈生成中位延迟 1.778 s，与首阶段翻译时间一致，体现两阶段架构开销可预测。
- 结论：模块化 ADS 与 LLM 自然语言接口结合的实践可行性得到验证，两阶段设计保障了反馈与实际执行状态一致，有助于建立用户信任。

## 7. 优点

- **架构解耦清晰**：语言理解与安全关键执行环路分离，显式白名单映射 + 参数边界校验构成可审计的安全层，避免将安全决策直接委托给 LLM。
- **应用中心 DSL 设计**：按交互语义而非软件模块组织，提升对内部架构变化的鲁棒性与跨栈可迁移性，理论上不限于 Autoware。
- **两阶段反馈机制**：基于确定性执行状态生成反馈，兼顾透明度与准确性，能向用户解释命令被拒的原因。
- **分类体系贡献**：五类交互分类可作为该领域描述、评估与标准化的通用框架。
- **工程实用性**：直接处理音频绕过 STT、云端推理规避车载算力限制、开源实现，具备向真车迁移的路径（已在研究车辆上初步确认）。
- **消融实验针对性强**：明确量化了 ICL 示例与 AV 状态信息各自的贡献。

## 8. 不足与局限

- **云依赖风险**：云端 LLM API 引入网络相关延迟与单点故障，实验中唯一的失败即源于此；离线/车载部署可行性未讨论。
- **模型未领域微调**：LLM 未针对驾驶领域微调，对歧义指令的鲁棒性未做系统性测试。
- **评估覆盖有限**：端到端定量评估仅限单一场景与单一地图，缺乏多样交通情境、多类指令组合与边界案例测试；真车仅做基础功能确认，无定量数据。
- **数据集偏置风险**：\(N=200\) 数据集为人工构造，指令风格与 DSL 配对可能无法代表真实乘客语言分布；多数指令不依赖上下文，可能低估 AV 状态信息的作用。
- **对比公平性存疑**：与 Song et al. 的对比在数据集、LLM、DSL 上均不同构，且对方数据经图像数字化提取，结论应谨慎解读。
- **功能范围限制**：尚不提供驾驶决策的因果解释；Intervention 类指令（如覆盖红灯）虽经安全校验，但其在真实道路中的合规性与安全边界未深入讨论。
- **延迟预算**：端到端响应约 1.7–1.8 s（单次 LLM 调用），对紧急干预类场景的实时性是否足够未做分析。
