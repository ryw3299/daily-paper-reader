## 摘要
车载助手必须在严格的内存和延迟约束下，将自然语言请求转化为准确的车辆函数调用，这使得小型语言模型（SLM）在设备端部署中颇具吸引力。对于此类模型，一个关键的设计选择是如何呈现可用的函数表面。两种方法是用专用的功能令牌（FT）表示每个函数，或直接在提示中提供函数模式。FT能够实现紧凑推理，但仅限于训练期间学习到的函数；而提示中模式（SIP）可以泛化到未见过的函数，代价是更长的提示和更高的推理开销。我们引入了一个包含9,822个单轮示例的基准，涵盖源自Android Automotive的79个车辆函数，包括留出函数和需要拒绝的请求。我们在四个参数量从270M到1.7B的SLM上，在匹配的微调条件下比较了这两种方法。在训练期间见过的函数上，扩展带来的收益有限：270M模型可以匹配1.7B模型，而我们主网格中最高的已见准确率出现在0.6B。在留出函数上，FT按构造实现零准确率，而SIP能够泛化并随规模显著提升。在范围外请求上，FT可能调用其被训练输出的不可用函数，而SIP基于所提供的函数更可靠地拒绝。这种灵活性伴随着更高的推理成本，主要是处理模式提示的延迟。我们的理论分析形式化了为什么只有SIP能够预测作为训练目标被保留的函数，以及为什么更长的模式上下文会增加推理成本。总体而言，函数表面表示而非仅模型规模，决定了基于SLM的车辆函数调用的能力和失败模式。

## Abstract
In-vehicle assistants must translate natural-language requests into accurate vehicle function calls under strict memory and latency constraints, making small language models (SLMs) attractive for on-device deployment. For such models, a key design choice is how the available function surface is presented. Two approaches are to represent each function with a dedicated Functional Token (FT) or provide function schemas directly in the prompt. FTs enable compact inference but are restricted to functions learned during training, whereas Schema-in-Prompt (SIP) can generalize to unseen functions at the cost of longer prompts and higher inference overhead. We introduce a benchmark of 9,822 single-turn examples spanning 79 vehicle functions derived from Android Automotive, including held-out functions and requests requiring refusal. We compare both approaches under matched fine-tuning across four SLMs from 270M to 1.7B parameters. On functions seen during training, scaling provides limited benefit: the 270M model can match the 1.7B model, and the highest Seen accuracy in our main grid occurs at 0.6B. On held-out functions, FT achieves zero accuracy by construction, whereas SIP generalizes and improves substantially with scale. On out-of-scope requests, FT can invoke an unavailable function it was trained to emit, while SIP more reliably refuses based on the functions offered. This flexibility comes with a higher inference cost, chiefly the latency of processing the schema prompt. Our theoretical analysis formalizes why only SIP can predict functions withheld as training targets and why longer schema contexts increase inference cost. Overall, function-surface representation, rather than model scale alone, determines the capabilities and failure modes of SLM-based vehicle function calling.

## 1. 核心问题与整体含义

- **背景**：车载语音助手需要把驾驶员的自然语言请求映射为准确的车辆功能调用（函数名 + 参数），错误调用可能直接驱动物理硬件（座椅、车窗、门锁等），因此可靠性要求远高于普通文本生成。
- **约束**：车载部署受限于内存、延迟、无网络连接，必须使用设备端小型语言模型（SLM，270M–1.7B 量级）。
- **核心问题**：对 SLM 而言，**如何向模型呈现“可用函数表面”（function surface）** 是一个关键设计选择。论文对比两种表示：
  - **Functional Token（FT）**：为每个函数分配专用词表 token，推理紧凑，但输出空间被训练时学到的函数锁死。
  - **Schema-in-Prompt（SIP）**：在输入提示中直接给出函数 schema（名称、描述、参数、取值约束），可泛化到未见函数，但提示更长、推理开销更高。
- **整体含义**：论文主张**函数表面表示方式（而非单纯模型规模）决定了 SLM 车载函数调用的能力边界与失败模式**，并给出理论解释与实证对比。

## 2. 方法论

### 2.1 核心思想
- 将 FT 与 SIP 形式化为**任务级输出支撑集（task-level output support）** 的差异：
  - FT：$\mathcal{Y}_{FT} = \mathcal{T} \cup \{\bot\}$，$\mathcal{T}$ 为训练时分配 token 的函数集，$\bot$ 表示拒答。因此对 $f \notin \mathcal{T}$ 有 $p_{FT}(f \mid x_i)=0$。
  - SIP：$\mathcal{Y}_{SIP,i} = \mathcal{O}_i \cup \{\bot\}$，$\mathcal{O}_i$ 为该样本提供的函数集合，因此留出函数只要出现在 $\mathcal{O}_i$ 中就可成为合法输出。
- 拒答判定：$\mathcal{C}(x_i) \cap \mathcal{O}_i = \varnothing \Rightarrow y_i = \bot$。SIP 显式看到 $\mathcal{O}_i$，FT 的评测形式不暴露该集合，故 FT 无法依据“当前不可用”拒答。

### 2.2 关键技术细节
- **基准构建（label-first）**：
  - 从 Android Automotive `VehiclePropertyIds` 提取可控属性，排除只读属性，转换为带参数约束的 schema（座舱区域作为参数，数值范围/枚举/布尔值作为合法取值）。
  - 先采样合法函数调用并用程序校验（函数身份、必填参数、类型、取值范围、适用区域），再用 Llama-3.3-70B-Instruct 生成自然语言请求，保证标签不依赖语言模型推断。
- **数据划分**：
  - Seen（56 个函数，训练目标中出现）、Unseen（18 个函数，按 8 个完整控制族整体留出，训练中仅作为非目标候选 schema 出现）、Out-of-Scope（5 个函数，从所有 offered set 中剔除）。
  - 每个样本的 offered set 含 4–24 个函数（中位数 14），Seen/Unseen schema 混合，防止通过候选集构成或排除法泄露答案。
- **质量控制**：目标泄漏检测（请求中不得出现函数标识符）、Mistral-Small-3.2-24B-Instruct 独立语义筛查、217 条分层人工核验切片（100% 忠实、99.1% 无歧义）。
- **理论分析**：
  - 用请求–schema 兼容性打分 $s_\theta(x,f)=\phi_\theta(x)^\top\psi_\theta(S(f))$ 与拒绝阈值 $\gamma_\theta$ 抽象选择/拒答行为，解释 SIP 如何通过“请求语言–schema 语言”的共享关系迁移到未见函数。
  - 推理成本：$L_{SIP,i}=|x_i|+|S(\mathcal{O}_i)|+c_{SIP}$ 远大于 $L_{FT,i}=|x_i|+c_{FT}$；稠密自注意力 prefill 约 $O(L^2)$，KV cache 线性增长。

## 3. 实验设计

- **Benchmark**：自建车辆函数调用基准，共 **9,822 条单轮英文文本样本**、**79 个函数**；训练 6,597 条、评测 3,225 条；最终计分分母为 Seen 545、Unseen 2,136、Out-of-Scope 533。
- **模型（4 个 SLM）**：
  - Gemma 3-270M（通用）、FunctionGemma-270M（函数调用专用预训练）——同规模对照；
  - Qwen3-0.6B、Qwen3-1.7B——同族容量对照。
- **训练设置**：FT 与 SIP 使用相同训练语料与优化配方（3 epoch、lr $2\times10^{-5}$、batch 16、最大长度 4096、warmup 0.03），每个配置 **3 个独立随机种子**；270M 与 0.6B 全参微调，1.7B 主网格用 LoRA。
- **对比方法**：FT vs SIP（同一模型、同一数据、匹配微调）。
- **指标**：Seen/Unseen 精确调用准确率；Unseen 额外报告 Execution（产出任意合法调用的比例）；Out-of-Scope 报告正确拒答率与 Over-trigger。
- **统计检验**：逐种子配对双侧精确 McNemar 检验（$\alpha=0.05$）。
- **设备代理（Device Proxy）**：GGUF Q4_K_M 量化 + llama.cpp，Xeon 8580 CPU 四线程、4096 上下文，测 time-to-first-call 与峰值 RSS（非车载硬件）。
- **消融**：Qwen3-1.7B 全参微调 vs LoRA；FunctionGemma 原生工具调用格式 vs 统一 JSON schema。

## 6. 主要结论与发现

- **Seen 函数接近饱和**：FT 与 SIP 在已见函数上均达 95.5%–98.7%，规模收益有限；主网格最高 Seen 准确率出现在 Qwen3-0.6B（SIP 98.7%）；FunctionGemma-270M 与 Qwen3-1.7B 的 SIP 在 Seen 上无显著差异（未证明等价）。
- **Unseen 函数**：FT 按构造为 0%；SIP 无需重训即可非零，且随规模显著提升（Qwen3-0.6B 59.3% → 1.7B 84.1%；Gemma 3-270M 15.6% → FunctionGemma-270M 18.6%，后者在三个种子上均显著更优）。
- **失败模式差异**：FT 在 Unseen 请求上 Execution 最高仅 6.0%，即多数拒答或输出无效，但一旦执行必为错误调用；SIP 的 Execution 与准确率差距较小（如 1.7B：87.9% vs 84.1%）。
- **拒答行为**：Out-of-Scope 上 SIP 正确拒答率 95.7%–98.4%，FT 为 81.4%–83.1%；差异集中在“请求的函数存在且 FT 有对应 token、但该函数不在 offered set 中”的情形（FT 拒答率仅 2.9%–5.1%，SIP 为 81.2%–93.5%）；当 FT 无对应 token 时两者均接近 98%–99.8%。
- **推理成本**：SIP 增加 1,785–1,905 个提示 token，time-to-first-call 为 FT 的 26–98 倍（如 Qwen3-1.7B：10,206 ms vs 104 ms）；单请求内存开销小，峰值 RSS 差异主要来自运行时 prompt cache（关闭后 0.6B SIP 接近 FT）。
- **部署建议**：FT 适合稳定函数面 + 严格延迟约束；SIP 适合函数面会变化（OTA、不同车型/配置）的场景；可组合使用（FT 覆盖高频稳定核心，SIP 兜底）；schema 前缀的 KV 状态可缓存复用；任何表示都不应无校验地驱动硬件。

- **问题定位清晰**：把“函数表面表示”从模型规模中剥离出来，作为独立设计变量研究，具有实际部署指导意义。

## 8. 不足与局限

- **数据合成性**：请求由 Llama-3.3-70B 生成，非真实驾驶员语料；仅英文、单轮、纯文本，未建模语音识别错误、多轮对话、车辆状态变化与依赖调用序列。

- **统计力度有限**：每配置 3 个种子；部分比较仅报告“未检测到显著差异”，不能证明等价。
- **效率评估局限**：仅单一 CPU 平台、Q4_K_M 量化、20 条请求、未测车载硬件；未评估量化对准确率的影响；未实测 KV 缓存复用、检索式候选裁剪、加速器等优化后的 SIP 延迟。
- **理论部分为抽象分析**：兼容性打分分解与泛化界仅为示意性论证，并非针对所用自回归模型的具体保证；in-context 示例的权衡仅有理论推导，无实验验证。
- **拒答与安全**：未测量 FT 加“不可用函数 token 掩码”后概率质量流向（拒答还是其他函数）；未讨论对抗性/歧义请求、安全关键功能的确认机制。
- **基准规模与覆盖**：79 个函数、5 个 Out-of-Scope 函数、18 个 Unseen 函数，覆盖面有限；Out-of-Scope 评测分母仅 533，细分后每组 n=92/164，统计粒度较粗。
