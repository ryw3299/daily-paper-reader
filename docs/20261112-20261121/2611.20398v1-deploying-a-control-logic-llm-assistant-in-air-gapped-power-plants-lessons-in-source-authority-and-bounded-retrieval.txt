# Deploying a Control-Logic LLM Assistant in Air-Gapped Power Plants: Lessons in Source Authority and Bounded Retrieval 

# Yiwei Fu, Nicholas Gabriel 

GE Vernova Advanced Research Center Niskayuna, NY, USA {yiwei.fu, nicholas.gabriel}@gevernova.com 

Abstract 

Deploying Large Language Model (LLM) assistants in indus-trial operational technology environments poses constraints largely absent from cloud applications: site policies restrict engineering and operational data from leaving the plant, on-premises compute is limited, and incorrect causal attribu-tion can mislead incident response. We report lessons from deploying a control-logic evidence layer that underpins a broader on-premises operator assistance system at two gas power plants. Two prototypes revealed where generative mod-els added avoidable uncertainty and cost. The first used a Vision Language Model (VLM) to reconstruct control topol-ogy from PDF printouts routinely exchanged by engineers. Across the full 6,979-page document, extraction reached 0.51 connection precision and required 3.1 hours on four H200 GPUs; consultation with controls engineers then revealed a native structured export from the authoring system. The sec-ond used an LLM tool-calling agent to plan repeatedly over eight predefined graph operations. In a controlled benchmark of 40 template-generated questions, replacing this agent with explicit execution plans reduced mean token use by 20 × and median latency by 3 ×, with identical retrieved node sets across repeated runs. The deployed design ingests the au-thoritative export into a versioned knowledge graph, executes bounded graph operations in fixed software, and confines the local LLM to fallback intent classification and evidence-grounded explanation. At one site, the graph contains 221K nodes across seven controllers. Our experience suggests a practical division of labor for high-consequence AI: LLMs interpret natural-language requests and explain results, while deterministic software constructs and retrieves technical ev-idence grounded in authoritative sources. Abstention, entity disambiguation, graph versioning, and read-only integration provide additional safeguards.

# 1 Introduction 

Power plants are governed by control logic comprising tens of thousands of sensors, function blocks, and signal dependen-cies. When a trip (emergency shutdown) or alarm occurs, an engineer traces backward through block diagrams and com-bines the resulting causal chain with event-time sensor data to determine what happened. The tracing step alone can re-quire hours of navigation through engineering tools and the expertise of a senior engineer. In this context, we use causal tracing to mean following cause-and-effect relationships ex-plicitly encoded in executable control logic; attributing a par-ticular event to one of those possible conditions additionally requires runtime measurements. Deploying a Large Language Model (LLM)-based AI as-sistant for this task requires understanding of the exact control logic of a plant, not just general control knowledge, because no two plants have identical configurations. Plant operational technology (OT) networks commonly prohibit sending live data to the public internet, ruling out cloud-hosted models. The assistant must run on constrained on-premises hardware, preserve exact signal paths, fail safely on unsupported or ambiguous requests, and remain synchronized with revised control configurations. Together, these constraints call for a local, versioned representation that preserves exact controller dependencies and supports deterministic, bounded traversal. We therefore transform the plant’s control logic into a knowl-edge graph (KG) layer for on-premises LLM-assisted causal tracing. These requirements make component allocation a deploy-ment decision. During development, we first used a Vision Language Model (VLM) to reconstruct topology from the routinely exchanged PDF printout. After it failed at full-document scale, we consulted controls engineers about the underlying source and learned that the authoring tool pro-vided a native structured export. A second prototype used an LLM tool-calling agent to plan repeatedly over a closed set of graph operations. We therefore ingest available struc-ture from its authoritative source, implement enumerable operations as bounded code, and limit LLMs to interpreting natural-language requests and explaining retrieved evidence. This task-boundary rule does not reject either technology: VLMs remain useful when no structured source exists, and agents when decomposition is genuinely open-ended. Prior work does not address this combination directly: industrial KGs rarely expose executable block-level logic, while agentic graph systems target broader query spaces (Section 2). We report how these constraints shaped a system now de-ployed at two gas power plants after validation on internal test systems. Its construction pipeline ingests the control system’s native Block Pin Report and builds a property graph contain-ing execution hierarchy, signal flow, and block equations. Its arXiv:2611.20398v1 [cs.AI] 16 Nov 2026 query pipeline maps natural-language requests to a bounded set of predefined operations, resolves entities, executes na-tive graph algorithms, and asks a local LLM to explain the retrieved evidence. Here, deterministic describes graph con-struction and execution after a query type and its entities have been selected; fallback intent classification and answer wording remain model-generated. Event-specific diagnosis remains grounded in runtime measurements and engineer-ing judgment. Our contributions to deployment practice are: 1. A deployment-derived rule for assigning tasks to gener-ative models versus deterministic software, supported by quantified accounts of an abandoned vision-based extrac-tion pipeline and tool-calling retrieval agent. 2. A deployed control-logic evidence pipeline that builds a versioned graph from an authoritative engineering export and maps natural-language requests to bounded execution plans, together with a controlled comparison against the agent it replaced. 3. Operational practices for air-gapped industrial AI: local inference, explicit resource bounds, out-of-scope absten-tion, entity disambiguation, read-only integration, and a clear boundary between dependency tracing and event-specific diagnosis from runtime data. 

# 2 Related Work 

Manufacturing knowledge graphs usually fuse lifecycle, equipment, process, and event data (Buchgeher et al. 2021; Ringsquandl et al. 2017b,a) or derive structure from stan-dards such as AutomationML (Grangel-González et al. 2018). Diagnostic KGs have also matched patterns in histori-cal service alerts (Wang, Qi, and Wu 2024). These represen-tations do not expose the executable block-level dependencies needed to trace a protection signal through controller logic. The closest work extracts alarm-related logic from PLC code before statistical root-cause learning (Wen et al. 2024); we instead represent complete production-scale control logic as a directly traversable evidence source. Natural-language access to structured data commonly uses text-to-SQL or text-to-Cypher (Liu et al. 2025; Ozsoy et al. 2025), while GraphRAG and Think-on-Graph delegate parts of multi-hop retrieval to model reasoning (Edge et al. 2024; Sun et al. 2023). Multi-Agent GraphRAG adds schema vali-dation, entity verification, and query refinement, yet reports 77% accuracy in its best benchmark configuration (Gusarov et al. 2025). These approaches target broader, open-ended query spaces. Our deployed interface instead exposes eight known operations, making traversal expressible as fixed plans; generative planning adds a variable failure mode without useful expressivity for this interface. Section 5.2 evaluates that task-specific choice rather than claiming that bounded execution replaces agents for open-ended work. Root-cause methods infer graphs from monitoring metrics, anomaly propagation, or industrial time series (Chen et al. 2014; Han et al. 2025; Wen et al. 2022); LLM agents have also shown limited performance when diagnosing incidents from raw observations (Roy et al. 2024; Xu et al. 2025). These methods are complementary: runtime data establishes what occurred during an event, whereas our graph exposes the programmed dependencies through which an observed condition can propagate. 

# 3 Deployed Evidence Pipeline 

The deployed layer has two pipelines (Figure 1): a graph con-struction pipeline that maps a structured control logic export to a knowledge graph, and a query pipeline that processes natural-language diagnostic questions against that graph. The graph acts as an inspectable contract between the authorita-tive source and the language interface: construction preserves source relationships, and query code returns an evidence pay-load that answer synthesis cannot modify. The construction pipeline ingests a Block Pin Report CSV, extracts entities and relationships in a single pass, and loads the resulting graph into an in-memory graph database. The query pipeline (Section 4) classifies incoming questions, resolves entity ref-erences, executes Cypher queries, and synthesizes a natural-language answer, using at most two LLM calls per query. 

3.1 Control Logic and Source Authority 

A gas turbine controller executes control logic : a large net-work of function blocks that runs cyclically, typically ev-ery few tens of milliseconds. Each block is a small typed operator—a Boolean gate, an arithmetic or equation block, a comparator, a timer, or a sequencer—with named input and output pins . Blocks are wired together by signals : a signal carries the value of one block’s output pin to the input pins of other blocks, forming a directed signal-flow network. An 

equation block stores a Boolean or arithmetic expression over its input pins; for example, (A+D)*~B*C is true when A or 

D holds, B is false, and C is true, where +, *, and ~ denote logical OR, AND, and NOT. Variables in these expressions are pin names local to the block, which is why the same ex-pression on two different blocks can refer to entirely different signals. Certain outputs are protection signals: when a protection signal transitions to true, the controller initiates a trip , an au-tomatic protective shutdown. Backward tracing reveals the programmed conditions that can produce that signal; iden-tifying which condition occurred in a particular event ad-ditionally requires runtime measurements. The GE Vernova Mark VIe ToolboxST engineering tool exports the block-and-pin structure of a controller as a flat CSV Block Pin Report ,the structured source our construction pipeline ingests. 

3.2 Construction from the Native Export 

The input to the graph construction pipeline is the Block Pin Report , a structured CSV export from the GE Vernova Mark VIe ToolboxST control system engineering tool. Each row represents a single pin on a single function block, with columns including Block , Block Type , Usage (Input, Output, or Const), Connection (signal name), Task , and

A Block Pin Report for a typ-ical heavy-duty gas turbine controller contains more than 100,000 rows, one per pin across all programs, tasks, and blocks; exact counts vary across models and site-specific configurations. 3.3 Preserving Signal Flow and Equations 

Signal-flow edges are derived directly from the Usage 

and Connection columns. A row with Usage=Input 

and a non-empty Connection produces a Feeds_Into edge from the named signal to the block; a row with 

Usage=Output and a non-empty Connection produces a Writes_To edge from the block to the named signal. Each edge carries pin metadata (name, description, data type) as properties, preserving the interface semantics. A single sig-nal may feed multiple pins on the same block (e.g., a tem-perature signal connected to both a comparison input and a display input), producing multiple Feeds_Into edges that preserve pin-level connectivity. Edges are deduplicated on the (signal, block, pin) triple to remove duplicate rows with-out collapsing distinct pin connections. Equation extraction targets blocks with a constant pin named EQN , whose Connection field contains the equa-tion string (e.g., I1+I2*I3 or (A*B*C)+(~E*D) ). A regular expression extracts symbolic variable names, which correspond to pins on the same block and identify the in-puts that participate in the expression. In our schema, equa-tions are stored as properties on Block nodes and inter-preted by the LLM during answer synthesis. An alternative schema we explored materialized equations as explicit Logi-cally_Feeds_Into edges between Pin nodes, enabling pure graph-based intra-block traversal without LLM involvement; Section 3.4 discusses this trade-off. 

3.4 Schema Decisions for Bounded Traversal 

Why model pins as edge properties rather than nodes 

An alternative schema models pins as first-class nodes, producing a 4-hop path for each signal-to-signal step (Signal →Pin →Block →Pin →Signal). Since native graph al-gorithms operate on hop counts, this doubled effective dis-tances and complicated depth limits. By folding pin metadata into edge properties, the deployed schema reduces each step to 2 hops (Signal →Block →Signal), forming a clean bipar-tite structure that BFS and shortest-path algorithms consume directly. Equations are similarly stored as block properties rather than materialized as inter-pin edges. Topological path discovery therefore treats connected inputs as dependencies, while the equation is retained for explanation and event-time interpretation. 

Why a graph database Control logic has two orthogonal relationship axes: a vertical execution hierarchy (Device →

Program → Task → Block) and a lateral signal-flow graph (Signal ↔ Block). A backward trace may cross very different numbers of blocks, so the implementation needs variable-depth BFS and shortest-path operations over both axes. Re-cursive relational queries could express these operations, but a property graph directly represents both relationship types while retaining typed pin metadata on edges. We use Falko-rDB, an open-source in-memory graph database; the schema and Cypher patterns are portable, although backend-specific graph procedures require adaptation. 

# 4 Bounded Query Execution 

The query pipeline maps a natural-language request onto a bounded set of graph operations rather than asking an LLM to generate Cypher or plan a traversal. Each request passes through classification, entity resolution, execution, and an-swer synthesis. Classification may use an LLM fallback, and synthesis always uses an LLM; entity resolution and graph execution are deterministic. Thus each request makes at most two model calls, while the retrieved nodes, edges, and paths are produced by fixed code under explicit resource bounds. 

4.1 Classification 

The classifier recognizes eight in-scope query types: block or signal inspection (explore_block, explore_signal, sig-nal_producers, signal_consumers) and dependency trac-ing (trace_upstream, trace_downstream, trace_between, sub-graph). A no-LLM fast path extracts composite block iden-tifiers and signal names, then applies phrase rules for intents including “what drives,” “feeds into,” and “path between.” Otherwise, an LLM selects one of the eight types or an ex-plicit unsupported-request outcome. The system abstains on unsupported requests rather than forcing them onto the near-est graph operation. 

4.2 Entity Resolution 

After classification, the pipeline resolves all extracted names in parallel using exact Signal.name , ex-act Block.name , and composite Block.block_id 

matches, with containment matching for composite iden-tifiers. A missing entity stops execution with a not-found response. When a short block name maps to multiple ex-ecution contexts, the system returns the candidate scopes and asks the user to disambiguate instead of choosing one silently. Centralizing this step avoids the repeated and po-tentially inconsistent lookups observed when a tool-calling agent decides for itself whether each name denotes a signal or block. 

4.3 Execution 

Each query type has a dedicated Cypher executor that re-turns both an evidence payload and visualization nodes and edges. Exploration operations retrieve adjacent signals and block metadata. Trace operations use native BFS or shortest-path procedures and enrich discovered blocks with their type, equation, pins, and connected signals in the same retrieval operation. The implementation caps trace depth ( ≤10 hops), BFS frontier size ( ≤8), and total node count ( ≤150), and bounds shortest-path length ( ≤16). The evidence payload records whether any bound truncated the result. Entity res-olution and retrieval therefore require two database round trips for the evaluated query types. 4.4 Evidence-Grounded Answer Generation 

The final stage serializes the retrieved evidence into query-specific context: block questions include equations and pin-to-signal mappings, trace questions include ordered depen-dency layers, and path questions include the node sequence. The LLM explains this evidence in natural language but cannot alter the graph payload shown to the user. Its prose remains LLM-generated and may vary or contain errors; the deterministic guarantee applies to the graph payload after intent and entity selection, not to the wording of the answer. Confining synthesis to retrieved evidence narrows the oppor-tunity for unsupported claims. Removing traversal planning from the model reduces context and computation enough for the evaluated local model to run on a single on-premises server (Section 6). 

# 5 Two Model-First Prototypes 

The deployed pipeline replaced two earlier model-first pro-totypes. Their failure modes differed, but the architectural cause was the same: the VLM inferred structure we later learned the authoring system could export, while the agent inferred an operation sequence that the application could enumerate. The following accounts explain why we replaced them and extract decision rules; they do not argue against VLMs or agents for open-ended tasks. We first establish the scale at which these design decisions operate. We evaluate the system on control logic from a gas power plant equipped with seven GE Vernova controllers. Experiments use one of the gas turbine controllers as the pri-mary unit, whose Block Pin Report contains 168,220 rows and produces the graph summarized in Table 1. To assess plant-level scale, we also construct the full graph spanning all seven controllers (gas turbine, safety controller, steam turbine, heat recovery steam generator, and balance-of-plant units); the number of controllers varies across sites. Con-struction time for the full plant graph remains under 30 sec-onds on a laptop. 

5.1 Lesson 1: Find the Source Before Extracting 

Our first graph construction prototype began from the con-troller’s 6,979-page control logic PDF, the artifact routinely exchanged by engineers. We exported each page as an im-age, sent it to a VLM, and parsed the extracted entities and connections into a graph. The structured export was not part of the usual exchange workflow and was initially unknown to the project team; moreover, outputs from individual pages looked plausible enough to suggest that scaling the prototype might work. Full-document processing exposed why that apparent suc-cess was misleading. The PDF was unsuitable as the source of record for three structural reasons: 65% of its pages were not diagrams and yielded spurious entities; labels visible in the printout did not consistently match internal pin and signal identifiers; and page-local extraction could not recover con-nections that crossed page boundaries. Downstream stages in our pipeline consumed rather than independently reval-idated the topology, so every trace and explanation inher-ited these errors. We therefore abandoned the VLM path and consulted controls engineers to identify an authoritative machine-readable source, which led us to the native Block Pin Report .Qwen 3.5-397B-A17B (Qwen Team 2026) reached 0.51 relaxed connection precision and 36% exact equation ac-curacy over the full document, compared with 75% equa-tion accuracy on the 100-page sample, and required 3.1 hours on four H200 GPUs (approximately $124). Gemini 3.1 Pro (Team et al. 2023) reached 0.24 connection precision and 4% equation accuracy on the shared sample. By contrast, the native Block Pin Report directly specifies block identity, pin direction, and connections and was ingested in under 10 seconds for the same controller. Because export records can-not be completely aligned with individual pages, the VLM study measures precision but not recall; it characterizes the false-positive burden of the rejected prototype rather than constituting a controlled comparison of equivalent inputs. Appendix A gives the full protocol and results. The transferable lesson is procedural rather than model-specific: source discovery should precede model selection. Before designing extraction from an engineering document, teams should identify its authoring system, ask domain engi-neers about native exports and APIs, and determine whether the document is a primary source or a rendered view. This rule also applies to piping and instrumentation diagrams (Al-imin et al. 2025), process-flow diagrams, and electrical single-line diagrams. A VLM may still recover information absent from structured sources, but it should not reconstruct relationships that those sources already encode. 

5.2 Lesson 2: Do Not Re-plan Enumerable Operations 

We compare the deployed classify-resolve-execute design with an earlier tool-calling prototype. Both use Qwen 3.5-35B-A3B-FP8 on an NVIDIA GB10 with 128 GB of unified memory, the same graph, and the same evidence-grounded synthesis prompt. The agent receives block, signal, path-tracing, and arbitrary-Cypher tools and decides which to call and when to stop; the deployed design selects a fixed executor after classification. The resulting decision rule is to enumerate before delegat-ing: when valid operations, parameters, and resource bounds can be specified in advance, classify once and execute a fixed plan. Agentic planning remains appropriate when valid task decomposition cannot be enumerated before execution. 

# 6 Production Deployment and Assurance 

The control-logic query layer is in operational use for post-trip analysis and alarm investigation at two gas power plants following validation on internal test systems. Starting from a protection signal, it surfaces upstream blocks, signals, and activation conditions as an interactive dependency graph; runtime measurements are then needed to determine which possible condition occurred. Appendix C provides a worked example for L86CBPS_F_A . Deployment exposed require-ments that are easy to miss in a laboratory prototype: offline operation, bounded resource use, safe handling of ambiguous requests, synchronization with changing control logic, and a clear boundary between decision support and plant control. 

6.1 Offline and Advisory by Design 

At the deployed sites, OT policies prevent data from leaving the plant, ruling out cloud-hosted models for this workload. The graph database, application, and local model therefore run on a single on-premises server. 6.2 Failure Containment and Configuration Lifecycle 

Natural-language interfaces create operational failure modes even when graph execution is deterministic. The deployed classifier can abstain on unsupported requests, and entity resolution asks for clarification when a short block name has multiple scoped matches. These controls prevent an appar-ently valid answer from being generated for the wrong opera-tion or component. Control configurations also change over a plant’s life. Each control logic graph is versioned and rebuilt from a new engineering export after configuration changes rather than mixing records from different revisions. Together with read-only integration, these practices keep the assistant advisory and make its evidence traceable to a specific source configuration. 

6.3 Retrospective Incident Replay 

We retrospectively replayed an October 2025 compressor bleed valve (CBV) trip from a unit where the system is de-ployed. The protection signal L86CBPS_F_A denotes dis-agreement between commanded and measured valve posi-tion. A backward query surfaced its RUNG_29 logic and the 

90CB1.POS_CV_DH position-deviation input (Figure 2; Appendix C gives the full query and response). A sepa-rate trip-analysis capability then evaluated archived histo-rian values: the command fell from 100 to 40 while feedback remained near 97, confirming that the valve did not move be-fore the trip. The replay demonstrates the intended division of labor—the graph assistant exposes the deterministic depen-dency structure, while runtime evidence establishes which condition occurred. 

6.4 Limitations 

Our evidence is subject to several limitations. Both evalua-tions use one vendor’s control format, and the query bench-mark uses a template-generated workload centered on one alarm. The LLM-generated answers are nondeterministic and were evaluated with an LLM judge rather than indepen-dent human review, although the underlying graph payload is preserved for inspection. Control logic and production code are proprietary and cannot be released. The reported field example is a single retrospective incident replay, and current site policies prevent the installations from exporting usage telemetry to a central service; we therefore report con-trolled technical measurements and deployment experience, not measured changes in operator response time or plant availability. Future work includes local privacy-preserving operational metrics and temporal reasoning over historian data. 

# 7 Conclusion 

We deployed a control-logic evidence layer at two air-gapped gas power plants. In these cases, the ability of a VLM or LLM agent to perform a step did not make it the appropriate pro-duction mechanism: the first reconstructed topology from the familiar PDF before we identified the authoring system’s native export, while the second re-planned eight enumerable graph operations. Replacing those steps with authoritative ingestion and bounded execution produced a 221,406-node plant graph and, in a controlled benchmark, reduced token use by 20 × and median latency by 3 × while returning iden-tical node sets across runs. The resulting division of labor is practical for high-consequence industrial AI: LLMs inter-pret natural-language requests and explain results; determin-istic software constructs and retrieves evidence grounded in authoritative sources; and runtime measurements plus engi-neering judgment establish what occurred during an event.

# A VLM Prototype Evaluation 

We evaluated Qwen 3.5-397B-A17B, hosted with vLLM (Kwon et al. 2023) on 4 ×H200 GPUs at FP8 quanti-zation, and Gemini 3.1 Pro. Each model received one page image and the same structured prompt requesting blocks, signals, connections, and equations as JSON. Both models processed the same seeded sample of 100 pages; Qwen ad-ditionally processed all 6,979 pages. Extracted entities were checked against the CSV-derived graph. We report precision only because the export records cannot be aligned completely to individual PDF pages; re-call is therefore unknown. Connection precision uses relaxed matching on (signal, block, direction) without requiring an exact pin name. Equation accuracy requires an exact equation match after scoping the block by program and task metadata from the page footer. This evaluation cannot establish total extraction quality, but it is sufficient to quantify false posi-tives in the rejected prototype. Observed failures included fully qualified visual tags sub-stituted for internal signal names, constants and pin labels emitted as signals, omitted negation operators, dropped equa-tion terms, incorrect program/task metadata, and connections lost at page boundaries. Table 3 reports the complete results.
