## Abstract 

Knowledge graphs on the Web are incomplete, and SPARQL an-swers a query only from the stored triples. Large language models (LLMs) can predict missing facts, but an LLM returns names instead of IRIs and requires one call per binding of a query variable. We present GenSPARQL, a generative extension of SPARQL 1.1 with an operator GENOP that binds values generated by an LLM to query variables during query evaluation. A similarity join maps generated names to entities of the graph, and the query planner invokes the LLM only for the bindings selected by the other graph patterns and filters. In a web workbench, attendees query two graphs built from Wikidata and inspect generated values, mapped entities and LLM calls. In our evaluation with three open-weight LLMs, the embedding similarity maps 83% of the entities named by the LLMs and yields only one incorrect match.

## 1 Introduction 

Knowledge graphs on the Web, such as Wikidata [13], are incom-plete [5]. SPARQL is the W3C-recommended query language for knowledge graphs in RDF [4]. A SPARQL query matches its graph patterns only against the stored triples [10]. For example, Figure 1 shows an excerpt of a knowledge graph of the 2026 FIFA World Cup with teams, groups and players from Wikidata. The query    

> SELECT ?pos WHERE { ?p ex:playsFor wd:Q79800 ; ex:position ?pos }

asks for the positions of the Argentine players and returns an empty result, because the graph models no playing positions. Large language models (LLMs) acquire factual knowledge during pretraining on Web documents such as Wikipedia articles [11] and generate candidate answers to questions about facts that a graph lacks, such as the positions and the World Cup titles of players. A SPARQL graph pattern relates a generated name to an entity only through an identical label and therefore cannot match variants such as Emiliano Martinez to the label Emiliano Martínez. Second, an LLM also generates names of entities outside the graph and names that denote no entity at all [6]. A name outside the graph can resemble the label of a different entity, so a comparison that tolerates variants can also produce incorrect matches. Third, a prompt with a query variable yields one LLM call per binding, such as one call per player. Four lines of existing work combine LLMs with queries over knowledge graphs. Text-to-SPARQL systems employ an LLM to translate a question in natural language into a SPARQL query [3], whose answers remain restricted to the stored facts. Work on LLM-augmented knowledge graphs [8] materializes facts inferred by an LLM in the graph before query evaluation and therefore spends LLM calls on all entities of the graph, including entities that no query reads. Retrieval-augmented generation over knowledge graphs [9] retrieves facts from the graph as context for an LLM and returns the answer of the LLM as text with names instead of IRIs, so a SPARQL query cannot use the named entities in further graph patterns. GraphDB invokes an LLM inside a SPARQL query through magic predicates and binds the generated text to a variable as a literal [7]. The query itself has to relate the literal to an entity of the graph. The mapping of generated names to entities of the graph thus remains outside the query engine. We present GenSPARQL, a generative extension of SPARQL. GenSPARQL extends the SPARQL algebra with the operator GENOP ,which invokes an LLM during query evaluation and binds the gener-ated values to query variables. Within the query engine, a similarity join [2] can map generated names to entities of the graph. A name matches an entity if the similarity between the name and a label of the entity reaches a threshold 𝜃 . ## 2.3 Query Planning and Implementation 

The planner orders the elements of a group as in the translation of Section 2.1, so GenSPARQL sends one prompt for every solution of 𝑃 in context mode and a single prompt in base mode. Filters without EXISTS over variables bound by the triple patterns of 𝑄 0

precede 𝐺 1 and remove solutions before the prompts. In Figure 2(a), the LLM is invoked for the 26 Argentine players out of the 1,248 players in the graph, wherever GENOP stands in the group. GenSPARQL extends the query engine ARQ of Apache Jena [1] with a parser for the syntax and compiles a query into the algebra of Section 2.1. The engine evaluates GENOP , the similarity join, FILTER 

and every OPTIONAL , MINUS or UNION that contains GENOP , and ARQ evaluates the other operators. GenSPARQL sends prompts to the Anthropic API, to OpenRouter and to OpenAI-compatible APIs, including those of the inference servers vLLM and Ollama for self-hosted models. The prompts request the generated tuples as a JSON array that is empty if the LLM has no answer. GenSPARQL obtains embeddings from OpenAI-compatible APIs and falls back to the Jaccard similarity if the embedding model fails. The default thresh-old 𝜃 0 is an engine parameter with the value 0.85. An HTTP service embeds the SPARQL server Fuseki and serves the workbench. 

## 3 Demonstration 

Attendees use GenSPARQL through a web workbench served by the HTTP service. The workbench offers the World Cup graph of Figure 1 (1,248 players, 48 teams) and a graph of 1,018 Nobel laureates. Attendees connect the workbench to an LLM and an em-bedding model through OpenAI-compatible endpoints and choose the embedding or Jaccard similarity and the threshold 𝜃 . The work-bench shows the answers, the number of LLM calls and a mapping view that connects each generated name with its matched entities. (1) Generating attributes. Attendees will use the chosen LLM to generate attributes absent from the graph, such as the positions in Figure 2(a) or the birth years of the Nobel laureates. The workbench compares the values generated by the three LLMs of Section 4 with Wikidata. (2) Mapping names to entities. Attendees will list the national teams of the World Cup or the fields of the Nobel Prize with a base-mode GENOP as in Figure 2(b) and vary the threshold 𝜃 . With both similarities at 𝜃 = 0.85, the similarity join maps neither United States nor Physics, because the graphs label the two entities USA and Nobel Prize in Physics. In the mapping view of the national teams, 𝜃 = 0.8 with the embedding similarity adds only incorrect matches such as Australia to USA. (3) Counting LLM calls. Attendees will ask for the players of Group A with the generated position defender or for the contributions of the Physics laureates since 2020. The work-bench replays each query step by step in the order of the planner and with GENOP evaluated first, and shows the LLM calls of both orders (Section 4). (4) Writing new queries and uploading graphs. Attendees will edit sample queries or write GENOP queries with prompts and patterns of their choice. Attendees can also upload a graph of their own as a Turtle file. 

Live and recorded modes. In the live mode, the service evaluates each query with the chosen LLM. At the venue, we will run the service, the workbench and Ollama with Mistral-7B and bge-large-en-v1.5 on one laptop, so the live mode works without Internet access. With Internet access, attendees can also choose remote endpoints such as a vLLM server or a hosted LLM provider. The recorded mode on the project page replays the queries of (1)–(3) with the answers of Qwen3-30B, Qwen3-8B and Mistral-7B from Section 4 and replaces the live mode at the venue if the live system fails. The workbench also runs from the repository with a local LLM and without a provider account. 

## 4 Evaluation 

We built the World Cup graph and the Nobel graph from Wikidata without the positions of the players and the birth years of the laureates. We evaluated GenSPARQL on both graphs with the open-weight LLMs Qwen3-30B-A3B-Instruct-2507, Qwen3-8B in non-thinking mode and Mistral-7B-Instruct-v0.3 at temperature 0 in the inference server vLLM. The embedding similarity used the model bge-large-en-v1.5. The repository contains the queries, the gold standard from Wikidata and the results.

Mapping names to entities. Six base-mode queries over the two graphs request lists of entities such as the teams of the World Cup and the fields of the Nobel Prize. Between 20% and 61% of the generated names of each LLM denote no entity of the graph (Table 1). The names of the three LLMs denote 145 entities of the graph, counted once per LLM. Precision and recall compare the mapped entities with the 145 entities. With the Jaccard similarity, the precision is 1 for 𝜃 ≥ 0.6and the recall at 𝜃 = 0.85 is 67%, because name variants such as Emiliano Martinez remain unmapped. ## 5 Conclusion 

We presented GenSPARQL, an extension of SPARQL with the op-erator GENOP . GenSPARQL answers queries with values generated by an LLM, maps generated names to entities of the graph and restricts LLM invocations to the bindings selected by the other graph patterns and filters. Every mapped entity belongs to the graph, whereas the correctness of a generated value depends on the LLM. Quantifying the uncertainty of generated values and of their mapping to entities and propagating the uncertainty through the evaluation of queries with GENOP remain open questions. 

## Ethical Use of Data 

The graphs contain public facts from Wikidata (CC0) and official records, including the citizenship and gender of the Nobel laureates. The evaluation involves no human participants, and the workbench collects no user data. Generated values about people can be incor-rect or biased and are not stored in the graphs. Names of people in prompts and embedding requests reach external servers only when users select remote endpoints.
