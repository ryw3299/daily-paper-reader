## Abstract 

An LLM agent that answers questions about a knowledge graph 

writes a program per question, and its tools evaluate each from 

scratch. We give the agent a  Datalog REPL , a session over a 

dynamic Datalog engine, in which rules are inserted and retracted 

like facts while derived facts stay current. Prompt caching reuses 

the model’s processing of what a session shares, and the Datalog 

REPL reuses the evaluation of it. On chains of questions over three 

knowledge graphs, agents reuse a relation that the REPL keeps in 

179 of 180 cases, with two models, and write fewer output tokens: 

SQL and Python agents write 23 to 82% more. With SQL tables 

or a Python namespace, Claude Haiku 5.5 stores almost nothing 

for later questions, and a chain of seven questions at 13 million 

facts takes it a median of 48 and 56 s, against 31 s with the REPL. 

Claude Opus 5.5 matches the REPL by storing tables in SQL, and 

when the data changes it stores views, which are evaluated again 

at every read. A relation that the REPL keeps is read like a table 

and stays current like a view. Datalog is a niche language beside 

SQL and Python, and with thinking enabled the models answer as 

accurately with it.

## 1 Introduction 

LLM agents increasingly act by writing code. In CodeAct  [20 ], the 

agent emits Python that a read  eval  print loop (REPL) executes, 

and the REPL keeps variables and definitions across turns, so later 

code builds on earlier results. Recursive Language Models give the 

model such a REPL with a long context held as a variable and 

calls to sub  models offered as functions  [23 ], and programmatic 

tool calling exposes the tools that allow it as functions that the 

generated code calls  [2].

Over a session, the prompt of such an agent grows. The system 

prompt stays, and every turn appends the agent’s code and the 

results it produced. Prompt caching exploits this. The model’s 

processing of a prompt, its attention states, can be stored and 

reused by a later request that contains the same declared segment 

of text  [9]. Commercial APIs store the processing of a prompt’s 

prefix and bill its reuse by a later request at a tenth of the input 

price or less  [3].

The evaluation of the agent’s code has no such reuse. Consider 

an agent that answers questions about a knowledge graph by writ 

ing queries. Many questions require recursion (“which organisa 

tions belong to this university, directly or indirectly?”) or inference 

from an ontology (“which employees work for this department?”, 

when the data records only full professors and lecturers). Over a 

session the agent writes a program for every question and revises 

it when a result looks wrong, and a query engine evaluates every 

version from scratch over the whole graph, however small the 

program and however much it shares with the programs before 

it. Materialized views, which store the results of a program and 

update them when the data changes, remove this cost for what 

the ontology implies  [11 ] [15 ]. The rules a question brings, and 

every revision of them, are evaluated from scratch by the engines 

that agents use. An agent can store a derived relation for later 

questions, as a table or a variable, but the copy is the agent’s to 

manage, and it goes stale when the data changes. 

Datalog states such questions compactly  [1]. A Datalog program 

is a set of rules, each of which derives facts from other facts. 

Recursion is an ordinary rule, an ontology is a set of rules written 

once, and a question adds a few rules and a query. Over a session, 

the agent’s Datalog program grows the way its prompt grows. 

A dynamic Datalog  engine accepts insertions and retractions of 

rules, as well as of facts, while it runs, and after each update it 

reports how the facts that the program derives have changed  [6].

Prompt caching reuses the processing of the prompt that a session 

shares, and a dynamic Datalog engine reuses the evaluation of the 

program that a session shares. We combine the two. A  Datalog 

REPL  is a session that holds a knowledge graph, its rules and every 

rule the agent has written, and applies each step of the agent as an 

update: the rules of a new question, or a revision of them. The facts 

that the graph’s ontology implies are computed once per session, 

each step is evaluated as an update to the facts derived before it, 

and the relations the agent defines persist as named rules, which 

answer later questions about any entity and stay current when the 

data changes, with no state for the agent to manage. 

We are not aware of prior work that gives an LLM agent a 

dynamic Datalog engine as its tool, or that relates the evaluation 

of an agent’s programs to prompt caching. Our evaluation has five 

findings.  Agents use what the session keeps.  With two models, Bruno Rucy Carneiro Alves de Lima and Victor Henrique Cabral Pinheiro 

they reuse a relation that the REPL keeps in 179 of the 180 cases 

where one applies and in 64 of 66 while the data changes, and they 

write fewer output tokens: the SQL and Python agents write 23 

to 82% more.  A small model gets no such reuse from SQL or 

Python.  With a persistent SQL database or Python namespace, it 

stores a relation in 2 of 288 cases, and on a graph of 13 million facts 

its chain of seven questions takes a median of 48 and 56 s, against 

31 s with the REPL.  A large model chooses in SQL between a 

table and a view.  It stores tables when the data is fixed, and its 

chains then take as long as with the REPL. When the data changes 

it stores views, which are evaluated again at every read. A relation 

that the REPL keeps is read like a table and stays current like a 

view.  The saving grows with the graph.  On all three graphs, 

a question on top of a kept relation saves more time the larger 

the graph is, up to 0.63 against 4.69 s. A change to the data costs 

about 1 ms, and at 13 million facts a one  rule revision of a program 

that keeps a large relation takes 2 ms as an update against 36 

s from scratch.  Datalog is a niche language, and the models 

are as accurate with it.  With thinking enabled, they answer as 

accurately in it as in the languages we compare it with, and an 

open model of 1.7 billion parameters answers recursive questions 

in Datalog alone. 

This paper makes three contributions. 

(1)  The Datalog REPL is a design for agent tools in which rules 

and facts are updates, answers are changes to the derived 

facts, and the derived facts persist across the questions of 

a session. 

(2)  A benchmark of 23 questions over three knowledge graphs 

labels each question by measuring what its reference pro 

gram needs, and an agent harness poses every question 

in Datalog, SQL, SPARQL and Python, each over the base 

facts and over all derived facts. 

(3)  An evaluation measures whether agents reuse what a 

session keeps, what that reuse saves against the SQL and 

Python tools that agents use, what a revision costs, and 

how accurately LLMs write Datalog. 

## 2 Related Work 

Reuse in LLM serving.  Serving systems reuse the model’s pro 

cessing beyond a single prompt prefix. SGLang’s RadixAttention 

caches the attention states of the prefixes that the calls of a 

language  model program share  [24 ], and semantic caches such 

as GPTCache store a model’s responses by the embedding of the 

query and return a stored response to a similar query  [8]. The 

Datalog REPL reuses the evaluation of the agent’s programs, and 

a kept rule answers later questions about any entity. 

Agents that keep what they computed.  Voyager stores an 

ever  growing library of executable code skills that later tasks re 

trieve  [19 ], and Agent Workflow Memory induces reusable work 

flows from past tasks  [21 ]. The Datalog REPL keeps the agent’s 

relations as rules whose derived facts the engine keeps current as 

the data changes. 

LLMs that write logic programs.  Faithful Chain  of  Thought 

translates a question into a reasoning chain in Python, Datalog or 

a planning language that a deterministic solver executes, so that 

the chain is a faithful explanation of the answer  [13 ], and Logic 

LM translates a problem into logic programs and other solver 

inputs and revises them from the solver’s error messages  [16 ].

The Datalog REPL keeps the solver’s state across a session, so the 

programs for one question build on those of earlier questions, and 

each revision is applied as an update. 

Incremental and dynamic Datalog.  DRed and counting  [11 ],

and recursive counting and forward/backward/forward mainte 

nance  [15 ], maintain the facts that a program derives while the 

given facts are inserted and deleted, DRed also while rules are 

inserted and deleted  [11 ], and IncA maintains the facts that a fixed 

program analysis derives as the analysed program changes  [18 ].

DDlog compiles a fixed program into an incremental dataflow 

[17 ] built on differential dataflow  [14 ], and Soufflé compiles a 

fixed program into parallel C++  [12 ]. DBSP derives the incremen 

tal version of a query, recursion included, from the query itself 

[4]. Earlier work evaluates differential dataflow as a backend for 

Datalog under frequent updates  [5] and applies incremental com 

putation to distributed ontology reasoning in which the ontology 

itself changes  [7]. The engine of  [6] evaluates dynamic Datalog 

programs, whose rules change at run time, as a higher  order DBSP 

program in which the rules themselves are inputs. 

Scope.  The REPL uses an extended implementation of an 

existing dynamic Datalog engine  [6], and our contribution is the 

design that exposes dynamic Datalog to an agent, together with 

its measurement. We compare the REPL with the SQL and Python 

tools that agents use, as the agents used them, on the recursive 

and derived relations that the questions need, and with no other 

reasoner. 

## 3 Background 

## 3.1  Datalog by example 

A Datalog program consists of facts and rules. A fact states a 

relationship between constants, as in  parentof(ann, bob) . A rule 

states that a fact follows from other facts. The two rules 

ancestorof(X, Y) :- parentof(X, Y). 

ancestorof(X, Z) :- parentof(X, Y), ancestorof(Y, Z). 

read: every parent of  Y is an ancestor of  Y, and every parent of an 

ancestor of  Z is an ancestor of  Z. Names that start with an upper 

case letter are variables. The second rule mentions  ancestorof 

on both sides of  :-, which makes it recursive. Predicates given by 

facts, such as  parentof , are  base  predicates, and predicates defined 

by rules, such as  ancestorof , are  derived  predicates. An engine 

evaluates a program by applying its rules to the facts until no new 

fact follows. The facts obtained this way, beyond the given ones, 

are the program’s  derived facts , and all facts together are its  closure .

A question is a query over base and derived predicates, possibly 

with rules of its own. The question “who are the ancestors of cid?” 

is the query  ?- ancestorof(X, cid). , and the question “which 

women are ancestors of cid?” becomes 

answer(X) :- ancestorof(X, cid), female(X). 

?- answer(X). 

The generated family graph of our evaluation starts its series of 

questions with these two.

## 3.2  Dynamic Datalog 

Keeping the derived facts current while base facts are inserted and 

deleted is known as incremental view maintenance  [11 ] [15 ], and 

compiled engines such as DDlog and Soufflé fix the program when 

they compile it  [17 ] [12 ]. A dynamic Datalog engine treats rules as 

input in the same way as facts. An update inserts or retracts rules 

and facts, and after each update the engine reports the change in 

the derived facts: the facts that now follow, and the facts that no 

longer do. The engine computes this change from the state it keeps 

between updates, instead of evaluating the program again from 

scratch  [6]. We use  materialized-view , an extended implementa 

tion of the dynamic Datalog engine of  [6] written in Rust, through 

its Python bindings, PyDYRE, at commit  b34efb0  of  github.com/ 

brurucy/materialized-view . It evaluates the higher  order DBSP 

program of that work, and we refer to it as the engine. 

## 4 A Datalog REPL for agents 

## 4.1  Sessions, updates and answers 

A session holds the base facts of a knowledge graph, the rules of 

its ontology, and the rules the agent has written, and a dynamic 

Datalog engine keeps the derived facts of all of them current. The 

agent uses one tool, which accepts a fragment of Datalog source 

and returns the answer to its query together with a summary of 

what the fragment changed. 

One tool call, step by step.  The REPL handles a call in four 

steps. 

(1)  It parses the fragment into rules, facts and one query, and 

checks them against the graph’s schema, the predicates 

that the session keeps and the engine’s limits, at most three 

terms in an atom and five variables in a rule. A fragment 

that fails a check is rejected with a message, and the session 

stays as it was. 

(2)  It takes the set difference with the program that it recorded 

for the current question, and applies it to the engine as one 

update, which retracts the rules and facts that the fragment 

drops and inserts those that it adds. 

(3)  It reads the answer to the query from the derived facts. 

(4)  It returns the answer rows and a summary of the update: 

for each predicate whose facts changed, the number of 

facts added and removed, with up to three examples, for at 

most ten predicates, the largest change first. 

Listing 1  shows two calls of one agent, on the two questions of 

the previous section, asked about person115 of a generated family 

graph. 

The state of a Python REPL is the namespace that results from 

executing statements in a particular order, and the state of a 

Datalog REPL is the set of derived facts of the current rules and 

facts. A revision is a difference. If the agent first omits  female(X) 

from the  answer  rule and adds it after seeing the result, the second 

step retracts the old  answer  rule and inserts the new one, and 

the  ancestorof  facts, which both versions share, are not derived 

again. The agent therefore writes complete programs, as it would 

in SQL or SPARQL, and the engine processes only their difference. 

A rule ends with a period and is undone exactly by its retraction, 

so the REPL can also apply each rule as soon as the model has 

generated it. 

The end of a question.  Questions share a session in one of 

three modes, and in all of them the knowledge graph and its rules 

are loaded once. In the  isolated  mode, the REPL retracts a question’s 

rules when the question ends, so every question sees only the 

graph and its own rules. In the  library  mode, the agent marks the 

predicates that later questions may use with a  .share  directive in 

its program. When the question ends, the REPL keeps the rules of Bruno Rucy Carneiro Alves de Lima and Victor Henrique Cabral Pinheiro

## 4.2  How an update is evaluated 

The engine has two inputs, the facts and the rules, and each input 

is a set of changes in which an insertion has the weight  +1 and 

a retraction the weight  −1 [6]. A rule enters as data. One entry 

per body atom records which atom a  partial match  of the rule, a 

binding of the variables matched so far, meets next, and which 

columns of that atom are bound by then, by a constant or by an 

earlier atom. One entry records the head to derive once the body is 

matched. Evaluation is a loop of four joins. Every fact is indexed by 

the bound columns of the body atoms over its predicate, a partial 

match is paired with the next atom of its rule, the indexed facts 

that agree with it on the bound columns extend it, and a match 

that has passed the last body atom yields its head as a new fact, 

until no new fact appears. Each join is a DBSP operator with 

incremental semantics, which computes the change of its output 

from the changes of its inputs and the state it keeps. An update 

therefore enters the loop as a change, and the engine reports the 

change in the derived facts, which the REPL’s summary counts by 

predicate. In  Listing 1 , the rule of the second question enters as one 

change and leaves as 17 new  answer  facts, and the summary lists 

no change to  ancestorof .

The REPL’s dialect is positive Datalog, the fragment that  [6]

evaluates. 

## 4.3  What a session changes and what it caches 

Over a session, four things change: the graph’s facts, the rules 

of each new question, the revisions of those rules, and the work 

available to the next question.  Table 1  lists which of them each 

kind of system that agents use today processes as an update. 

Prompt caching and the Datalog REPL combine in one session: 

the prompt that describes the graph’s schema and rules is cached 

on the model side, and the graph’s derived facts are cached on the 

evaluation side. A prompt cache reuses the model’s processing of a 

prefix that an earlier request shares, and everything after the first 

changed token is processed again. The REPL reuses the derived 

facts of every rule already in the session, in any order, and a change 

updates only the consequences of the changed rules. 

## 5 Evaluation 

We ask four questions. RQ1: do agents reuse what a session keeps, 

across questions and while the data changes? RQ2: what does the 

reuse save, against the SQL and Python tools that agents use? RQ3: 

what does a revision cost? RQ4: are LLMs as accurate when they 

write Datalog, a niche language, as when they write SQL, SPARQL 

and Python? 

## 5.1  Knowledge graphs and questions 

We use three knowledge graphs ( Table 2 ). LUBM  3 consists of 

universities 0 to 2 of the LUBM benchmark  [10 ] with the Univ 

Bench ontology. Follows is a generated network of 12 communities 

of 25 accounts each, with cycles inside every community and one 

way links between communities. Family is a generated genealogy 

of 159 people over six generations, the graph of  Listing 1 . Together, 

the questions of the three graphs require joins, ontology inference 

and recursion. 

Every question has a reference program in Datalog, and every 

label of a question is a measurement on its reference program. 

What a question adds to the graph’s predicates is a  lookup  when its 

program has no rules of its own, a  join  when it has rules without 

recursion, and  recursion  when one of its rules is recursive. The Cache the Knowledge, Not Just the Prompt: Dynamic Datalog as the Action Language for LLM Agents 

build of the question set rejects a question if removing any one

The derived facts of LUBM  3 match those of an independent OWL

## 5.2  Agent harness and conditions 

Eight conditions combine one of four languages with one of two 

kinds of data. In the conditions marked M, programs run over the 

graph with all derived facts available, which is what a Datalog 

REPL holds once the graph’s rules are loaded, so the agent writes 

only what the question adds: a query and helper rules in Datalog, 

SQL, SPARQL 1.1, or a Python function that returns the answer 

rows. In the conditions marked B, programs run over the base facts 

alone, and the agent also writes the graph’s reasoning. Datalog 

runs in a Datalog REPL, SQL in DuckDB 2.0.0, SPARQL in Oxigraph 

(pyoxigraph 0.5.13), and Python in a sandbox without network 

access. 

Every condition receives a system prompt with the same sec 

tions in the same order, and the graph’s rules are stated as the 

same English sentences in every condition, so that no language 

receives them in its own syntax. In an agent loop that interleaves 

reasoning and tool calls  [22 ], the model writes a program, runs it 

at most three times through the condition’s tool, reads each result, 

and submits a final program. In the Datalog conditions, the REPL 

applies each run as an update to the program of the previous run, 

and the agent is not told so. The scorer runs the submitted program 

again and compares its answer rows with the gold answers as sets. 

We report the rate of exact matches and the F1 score over answer 

rows. The model is Claude Haiku 5.5 with adaptive thinking at high 

effort, each question is run three times, each run an  epoch , and the 

harness is inspect  ai 0.3.285. The independent questions are also 

run in two further settings: the same model with thinking turned 

off, and LFM3  1.7B, an open model of 1.7 billion parameters, run 

locally in one epoch. 

## 5.3  Sessions 

Independent samples measure accuracy, and they leave nothing for 

a later question to reuse. A session poses several questions about 

one graph to one agent, one after the other, in one conversation 

and with one REPL, in the Datalog  B condition, so the agent writes 

every rule that a question needs, including the graph’s rules. 

The independent questions share few rules beyond the graph’s, 

so we also pose  chains  of questions about one graph that build on 

one another: seven on LUBM  3, four on Follows and five on Family, 

whose first two questions are those of  Listing 1 . Each question 

is self  contained, and 12 of the 16 have a reference program over 

the base facts that defines a predicate with exactly the rules of an 

earlier question, such as the reachability relation of Follows, asked 

about account30 and later about account130. A question reuses an 

earlier predicate  by name  when its program reads a kept predicate 

without defining it, and  by its rules  when it states a kept predicate 

with the same rules, an empty update. Otherwise it  restates  an 

earlier question’s rules, which the engine derives again, or defines 

what it needs anew. 

We compare the Datalog sessions with two sessions that keep 

what the agent computes: a Python REPL whose namespace per 

sists across questions, as in CodeAct  [20 ], and a DuckDB database 

whose tables and views persist. A view is a named query that the 

database evaluates again at every read, and DuckDB has no view 

that it keeps up to date. In the chains, their prompts state, as the 

Datalog prompts do, that a relation computed for one question is 

often needed again, and their results list what earlier questions 

stored. Each chain is posed twelve times in all five kinds of session 

with Claude Haiku 5.5, and three times in the isolated, keep  all, 

SQL and Python sessions with Claude Opus 5.5, a larger model of 

the same family, with the same thinking setting. A question in one 

session is a  case , so the 12 questions that can reuse give 144 cases 

for each kind of session with Haiku and 36 with Opus. 

## 5.4  Measurement and statistics 

Replays.  To time the engine on larger graphs, we replay the 

agents’ LUBM  3 programs, in the order each sample ran them, on 

LUBM  10, LUBM  30 and LUBM  100, universities 0 to 9, 0 to 29 and 

0 to 99 of the same generator, with the same 99 rules and 1.3, 4.0 and 

13.4 million base facts. Scored against gold answers computed at 

each size, the co  authorship question (authors connected through 

chains of co  authorships) aside at LUBM  100, every Datalog pro 

gram that is correct on LUBM  3 is correct there, and every wrong 

one stays wrong. Every time we report for LUBM is this replay on 

LUBM  100, with eight worker threads of the engine, on an Apple 

M5 Max with 18 cores and 48 GB of memory. The sessions on 

Follows and Family are replayed on their own graphs and on larger 

graphs from the same generators: Follows with 10, 30 and 100 times 

the communities, and Family as 100 and 1,000 genealogies. A time 

is a single run unless we give the number of runs. A question’s 

engine time  in a session is the time of its runs and of the update that 

ends the question. Times that depend on the model are measured 

by sending its requests again through the streaming API, with 

the tool’s input streamed as it is generated and the thinking text 

omitted. The calls of all kinds of session of a model are sent in the 

same minutes, one kind beside the other. In every replay of this 

paper, the update and the evaluation from scratch give the same 

answer. 

Statistics.  Comparisons are paired by the unit named with 

them, and tests are two  sided: an exact sign test or a Wilcoxon 

signed  rank test for paired measurements, an exact Mann  Whit 

ney test for two groups of sessions, an exact McNemar test and 

Cochran’s Q for paired correctness, Fisher’s exact test for counts, 

and Holm’s correction within a family. Intervals are 95% bootstrap 

intervals.

## 5.8  RQ4: accuracy in a niche language 

We expect Datalog to be far rarer in a model’s training data than 

SQL or Python, and with thinking the models are nevertheless as 

accurate with it. In the chains of both models, the keep  all, SQL 

and Python agents answer every question exactly ( Table 3 ). On the 

independent questions ( Table 5 ), every condition answers 65 to 69 

samples exactly with thinking, and the four languages do not differ 

on either kind of data (Cochran’s Q,  𝑝  = 0.29 and  0.72). Compared 

with each other language on the same data by an exact McNemar 

test over the 69 pairs of a question and an epoch, neither Datalog 

condition differs significantly ( 𝑝  ≥ 0.25 in the six comparisons): the 

Datalog conditions answer 1.4 to 4.3 points fewer samples, with 

95% intervals between  −11.6 and  +4.3 points. Without thinking, 

every condition answers 55 to 69 samples exactly, and the four 

languages differ ( 𝑝  = 0.002 and  0.003). After Holm’s correction, no 

difference between a Datalog condition and another language is 

significant ( 𝑝  ≥ 0.09). LFM3  1.7B answers 8 to 12 of the 23 samples 

of each condition exactly, and the four languages do not differ ( 𝑝  =

0.48 and  0.52). Only in Datalog does it answer any of the three 

recursion questions: 3 of its 6 attempts, against none of the 18 in 

the other languages (Fisher’s exact test,  𝑝  = 0.01). 

## 5.9  Generality 

The reuse of RQ1 holds on each of the three graphs, with the data 

fixed and with the data changing, and with two models ( Table 3 ). 

The time that a kept predicate saves grows with the graph on all 

three graphs, and with what the kept rules derive ( Figure 1 ). The 

single  rule revision is faster as an update at LUBM  100 in each of 

the three model settings, by a median factor of 2.6, 1.9 and 2.9, and 

on both kinds of data, by 2.0 and 2.1. 

## 6 Conclusion 

A Datalog REPL gives an LLM agent a tool whose state is the 

set of facts that follow from the rules it has written, kept current 

by a dynamic Datalog engine. Prompt caching reuses the model’s 

processing of what a session shares, and the Datalog REPL reuses 

the evaluation of it. Agents reuse a predicate that the REPL keeps 

in 179 of 180 cases with two models, and in 64 of 66 while the data 

changes, and the SQL and Python agents write 23 to 82% more 

output tokens. With SQL tables or a Python namespace, a small 

model stores almost nothing for later questions, and at 13 million 

base facts its chain of seven questions takes a median of 48 and 56 

s against 31 s with the REPL. A large model matches that time by 

storing tables in SQL, and when the data changes it stores views, 

which are evaluated again at every read. A predicate that the REPL 

keeps is read like a table and stays current like a view, and the 

time it saves grows with the graph on all three graphs. Datalog is 

a niche language beside SQL and Python, and with thinking the 

models answer as accurately with it.
